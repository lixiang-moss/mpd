# DMEval vNext（L1）实现思路与取舍说明

本文档专门回答“我为什么这么写、核心设计如何对应 `工具描述文档.md` 的规格”，方便你在论文里解释框架设计。

## 1. 对规格的逐条映射（从原则到代码）

### 1.1 L1 解耦：只编排，不侵入 MPD

- DMEval 侧只做两件事：  
  1) 串行调用被测系统（subprocess）  
  2) 从产物目录抽取/聚合/比较（CSV/plots）
- **不在 DMEval 里重算指标**：实现上只读取 `trial_metrics.jsonl` 或 `.pt` 里的已有字段，做 `mean/std` 聚合与排序。
- 对应代码：
  - `dmeval/src/dmeval/runner.py`：只负责拼命令与跑子进程
  - `dmeval/src/dmeval/adapters/mpd.py`：只负责“读产物并抽字段”
  - `dmeval/src/dmeval/collect.py`：只做聚合（trial→run→agg）

### 1.2 Hydra 只在 DMEval（compose API）

你要求的关键点是“Hydra 只用于配置组合/覆盖，不接管 cwd/outputs/launcher”。因此：
- DMEval 用 `hydra.initialize_config_dir + compose(...)` 加载配置，不用 `@hydra.main`
- Hydra 只用于：
  - defaults 组合（planner / adapter / objective）
  - 命令行 overrides 覆盖（例如 `-o common_inference_args.device=cuda:0`）
- 对应代码：`dmeval/src/dmeval/config_loader.py`

### 1.3 两阶段范式：Stage I 调参 → Stage II 公平对比

- Stage I（tune）职责：对每个 sampler 找到一个（或 top-k）代表性配置，并固化为 `best_patch.yaml`
- Stage II（compare）职责：读取 Stage I 的 `best_patch.yaml`，在多个 scenario 上做公平对比并输出排名/图
- 对应代码：
  - `dmeval/src/dmeval/stage_tune.py`
  - `dmeval/src/dmeval/stage_compare.py`

### 1.4 “阈值 + 排序/评分”的 Objective

实现上我把 Objective 拆成两层：
- Constraints：不满足阈值直接判 infeasible
- Ranking：
  - 当前默认实现：lexicographic（多指标字典序排序），更容易跑通闭环且不纠结权重
  - 预留：score（标量分数）接口，为 Optuna/贝叶斯留口子
- 对应代码：
  - `dmeval/src/dmeval/objective.py`：`select_topk(...)`
  - 默认配置：`dmeval/conf/objective/lexicographic.yaml`

### 1.5 Adapter 层：优先 jsonl，回退 pt

规格要求：
- 优先读 `trial_metrics.jsonl`（若 MPD 做轻量输出）
- 否则回退读 `.pt`

实现方式：
- `MPDAdapter.collect_trial_rows()` 先扫描 `trial_metrics.jsonl`，有就用 jsonl；否则扫描 `results_single_plan-*.pt` 并 `torch.load`
- 注意：为了不强依赖 torch，我把 `import torch` 放在 `.pt` 分支里（jsonl 分支不需要 torch）
- 对应代码：`dmeval/src/dmeval/adapters/mpd.py`

## 2. 输出契约（为什么这样组织目录/文件）

你在规格里强调了可追溯性，因此每个阶段都做了：
- 统一 pipeline 根目录：`pipeline.root`
- Stage I 输出：
  - `tune/<sampler>/trial_metrics.csv` / `run_metrics.csv` / `candidate_metrics.csv`
  - `best_configs/<sampler>/best_patch.yaml` / `topk.yaml` / `best.yaml`
  - `tune_manifest.yaml`（包含 resolved config）
- Stage II 输出：
  - `compare/trial_metrics.csv` / `run_metrics.csv` / `run_metrics_agg.csv`
  - `compare/rank_*.csv` / `compare/plots/*.png`
  - `compare/compare_manifest.yaml`

这些文件名都尽量贴近你写论文时的“trial/run/candidate”层次，且避免依赖 Hydra 的输出目录体系。

## 3. 一些刻意的取舍（为什么暂时这样做）

### 3.1 为什么暂时没把 Optuna 做进默认闭环

规格里写了 “optuna（P1 可选实现）”。我选择先把 grid/random + 闭环跑通：
- 论文/导师验收更关心“能否复现、能否公平对比、产物是否规范”
- Optuna 属于锦上添花，但引入依赖与调参逻辑会增加维护成本

代码里目前对 `search.strategy=optuna` 会明确报错提示（不会静默失败），以后你要上 Optuna 可以在 `dmeval/src/dmeval/search.py` 里扩展。

### 3.2 为什么 Stage I 里增加了 candidate_metrics.csv

规格要求输出 trial/run 两层 CSV；但 Stage I 的 objective 是按 **candidate** 选 best：
- run_metrics 是按 seed 聚合
- candidate_metrics 是跨 seed/trials 的聚合（用于 constraints/ranking）

为了让“为什么选这个 best”可解释且可复查，我把 candidate_metrics 作为独立产物输出。

### 3.3 为什么增加 dummy planner

你要求“最小端到端样例”。但 MPD 在不同机器/容器里可能涉及 GPU/IsaacGym/数据路径等复杂依赖。

因此我提供了 `dmeval/scripts/dummy_planner.py`：
- 只输出 `trial_metrics.jsonl + args_inference.yaml`
- 用于快速验证 DMEval 的闭环正确性（Stage I→II、CSV、plots、rank）
- 不替代 MPD，只是一个可控的 smoke test

## 5. 本工具如何读取/组织实验数据（机制与细节，以 MPD 为例）

这一节专门回答“DMEval 怎么读实验数据、文件之间的关系、以及是否兼容 MPD 这种一次 run 内包含 N 个 trial 的情况”。

### 5.1 先明确：DMEval 读的不是“日志”，而是“产物目录”

DMEval 的数据来源是被测系统（如 MPD）在一次 inference 后落盘的**结构化产物**，而不是 console log。

因此 DMEval 的核心工作流是：
1) 通过 `runner.py` 串行启动被测系统子进程（一次 run）
2) 等子进程结束后，在约定的结果目录下发现产物文件
3) 通过 Adapter 把产物文件解析成统一口径的 `trial_rows`（每个 trial 一行）
4) 用 pandas 做聚合（trial → run → candidate/agg）并输出 CSV/plots/rank

这样做的好处是：
- 不依赖 MPD 的 sweep/launch 脚本（符合规格）
- 不依赖 log 格式（log 很容易变且不适合做结构化比较）
- “只抽取、不重算”：指标值仍由 MPD 负责计算并写出

### 5.2 Stage I / Stage II 的落盘目录是 DMEval 自己管理的

所有输出都在 `pipeline.root` 下（由配置决定）。以 Stage I 为例，每个 sampler 下会有 candidates 子目录：

```
<pipeline.root>/
  tune/
    <sampler>/
      candidates/
        c0000/
          patch.yaml
          cfg_inference.yaml
          seed2.log
          results/
            2/...
        c0001/
          ...
      trial_metrics.csv
      run_metrics.csv
      candidate_metrics.csv
  best_configs/
    <sampler>/
      best_patch.yaml
      best.yaml
      topk.yaml
  tune_manifest.yaml
```

关键文件的作用：
- `patch.yaml`：一个 candidate 的“覆盖项”（最重要的复现材料之一）
- `cfg_inference.yaml`：base_cfg + patch 合并后的最终推理配置（便于人工检查）
- `seed*.log`：该 candidate 在该 seed 下运行子进程的 stdout/stderr（排障用）
- `results/`：子进程真正写出来的结果根目录（MPD 会在里面创建 seed 子目录）

Stage II 类似，只是目录维度变成 scenario × sampler：

```
<pipeline.root>/compare/
  <scenario>/<sampler>/
    cfg_inference.yaml
    seed2.log
    results/2/...
  trial_metrics.csv
  run_metrics.csv
  run_metrics_agg.csv
  rank_*.csv
  plots/*.png
  compare_manifest.yaml
```

### 5.3 MPD 的“一个 run”为什么会产生 N 个 trial？DMEval 如何理解它？

按你的术语定义：
- Run = Candidate × Seed（一次调用 inference）
- Trial = run 内的一个 start-goal 规划尝试
- N = `n_start_goal_states`

在 MPD 里，传入 `--n_start_goal_states N` 后，MPD 会对 N 个 start-goal 依次产生结果文件。

典型（默认）产物是：
- `results_dir/<seed>/args_inference.yaml`
- `results_dir/<seed>/results_single_plan-000.pt` ... `results_single_plan-(N-1).pt`

如果你在 MPD 侧做了轻量输出（推荐）：
- `results_dir/<seed>/trial_metrics.jsonl`（每行一个 trial 的指标）
- （可选）`results_dir/<seed>/run_summary.yaml`（run 聚合统计）

DMEval 的设计就是围绕这个“run 内 N 个 trial”的结构来的：它把每个 trial 当成一行记录，然后再做聚合统计。

### 5.4 Adapter 的具体读取机制（MPDAdapter）

MPDAdapter 的目标是：**把“MPD 的产物目录”变成“统一字段口径的 trial 行 dict”**。

入口函数是 `MPDAdapter.collect_trial_rows(results_root=...)`，它会：

1) 递归扫描 `results_root`，寻找每个 seed 目录下的轻量文件：
   - 如果存在 `trial_metrics.jsonl` 且 `prefer_jsonl=true`：优先读取 jsonl
2) 否则回退扫描 `results_single_plan-*.pt`：
   - 对每个 `.pt` 用 `torch.load` 读出 `result.metrics` 并抽字段

同时它会在同一个 seed 目录里读取：
- `args_inference.yaml`：补齐 `planner_alg`、`diffusion_sampling_method`、`env_id_replace` 等元信息

为什么必须读 `args_inference.yaml`：
- 这能把“这次推理到底用了什么 planner_alg/sampler 方法”等信息与结果绑定在一起
- 即使你在 DMEval 侧额外记录了 `sampler/candidate_id`，也建议保留 MPD 自己的元信息作为交叉校验

对应代码：`dmeval/src/dmeval/adapters/mpd.py`

### 5.5 trial → run → candidate 的聚合逻辑（解决你说的“统计意义”问题）

你提到的关键点非常重要：MPD 一次 run 内有 N 个 trial，**单条 trial 没有统计意义**，必须聚合。

DMEval 的兼容性体现在它明确做了两层聚合：

1) **Run 级聚合（candidate × seed）**  
   在 Stage I，DMEval 先把 trial_rows 变成 trial_df，然后按：
   - `["scenario","sampler","candidate_id","run_tag","seed"]`
   做 `mean/std` 聚合，得到 `run_metrics.csv`。

   这一步的 `*_mean`（比如 `success_mean`）就是“同一 seed 下 N 个 trial 的平均成功率”等统计量。

2) **Candidate 级聚合（跨 seed）**  
   Stage I 的 objective 需要在 candidate 级别选 best，因此再按：
   - `["scenario","sampler","candidate_id"]`
   做 `mean/std` 聚合，得到 `candidate_metrics.csv`，并用它进行阈值过滤与排序。

Stage II 同理：
- `run_metrics.csv`：按 (scenario,sampler,seed) 聚合
- `run_metrics_agg.csv`：按 (scenario,sampler) 聚合（跨 seed），用于公平对比/绘图/排名

因此，像你说的 “一次 run/配置 内跑 N 次 trial，只有把这 N 次聚合平均才有意义”——DMEval 是**天然兼容**的，并且把这件事当作核心契约来实现。

对应代码：`dmeval/src/dmeval/collect.py` + `dmeval/src/dmeval/stage_tune.py` + `dmeval/src/dmeval/stage_compare.py`

### 5.6 Stage II 如何保证“同一 best 配置”跨场景复用（与 MPD 的衔接）

Stage I 输出的关键文件是：
- `best_configs/<sampler>/best_patch.yaml`

Stage II 的做法是：
- 对每个 scenario 的 base_cfg（MPD inference yaml）
- 应用同一份 `best_patch.yaml`（深度合并）
- 得到该 scenario 下该 sampler 的最终 `cfg_inference.yaml`

这就实现了你论文里要强调的“公平对比”：不同 sampler 都用自己的 best_patch，但在不同 scenario 下保持同一套 best_patch 逻辑，避免手工改 cfg 带来的偏差。

### 5.7 结果文件很多会不会很慢？有什么优化方向？

当 MPD 只输出 `.pt` 时，DMEval 需要扫描 N 个 `.pt` 并逐个 `torch.load`，这确实可能慢。

因此规格里建议 MPD 增加轻量输出：
- `trial_metrics.jsonl`：DMEval 可完全避免读取 `.pt`
- （可选）`run_summary.yaml`：DMEval 甚至可以直接读聚合结果，避免再聚合

当前实现已经支持 **jsonl 优先、pt 回退**；`run_summary.yaml` 作为进一步优化点预留（配置里已有字段，但代码未强依赖它）。
