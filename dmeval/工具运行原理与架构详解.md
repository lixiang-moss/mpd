# DMEval vNext（L1）运行原理与架构详解

话题先放在最前面：**DMEval 是一个“评测管线工具”。**  
它不算指标。它不改 MPD。  
它做三件事：**跑实验、读产物、出对比结果**。

---

## 1. 你拿它来做什么

输入。两类输入：
- 一份 DMEval 配置（Hydra YAML）。它决定实验矩阵。
- 一套被测系统（例如 MPD）。它负责推理与写指标。

输出。一套统一产物：
- `trial_metrics.csv`：trial 级指标表
- `run_metrics.csv`：run 级聚合表
- `candidate_metrics.csv`：candidate 级聚合表（Stage I 用）
- `best_configs/<sampler>/best_patch.yaml`：Stage I 的结论。Stage II 的输入
- `rank_*.csv`：排名表
- `plots/*.png`：基础图
- `*_manifest.yaml`：复现记录

---

## 2. 先把名词说清楚（这套词要一直用）

Scenario。一个评测场景。对应一份 MPD base inference YAML。  
Sampler。一个采样器。例：ddim / dpm_solver_pp / unipc。  
Candidate。一套候选超参。例：steps=26, order=2, pw=1.05。  
Run。一次运行。它等于 Candidate × Seed。它会调用一次 inference。  
Trial。一次尝试。它是 run 内部的一条 start-goal 规划。  
Seed。随机种子。用于可复现。  
N。`n_start_goal_states`。一个 run 内 trial 的数量。

一句话总结：  
**DMEval 以 Trial 为原子数据。它在 Run/Candidate 层做统计。**

---

## 3. 这工具“通用”在哪里

通用点。放在流程层：
- Stage I：调参。产出 best_configs。
- Stage II：对比。读 best_configs，跨场景跑公平对比。
- 数据层：trial → run → candidate/agg 聚合。
- 产物层：CSV/plots/manifest 的文件名与字段口径固定。

非通用点。放在解析层：
- 不同 planner 的产物格式不同。
- 字段名也不同。

结论：  
**DMEval 把“解析差异”放进 Adapter。主流程保持稳定。**

---

## 4. 分层结构（你可以用它画架构图）

四层就够用：

1) 配置层（Hydra compose）
- 位置：`dmeval/src/dmeval/config_loader.py`
- 功能：合并 defaults。应用 overrides。
- 不做：不接管 cwd。不开 Hydra outputs 目录。不开并行 launcher。

2) 管线层（Stage I/II 编排）
- Stage I：`dmeval/src/dmeval/stage_tune.py`
- Stage II：`dmeval/src/dmeval/stage_compare.py`
- 功能：决定“跑谁、跑几次、结果写哪”。

3) 执行层（Runner）
- 位置：`dmeval/src/dmeval/runner.py`
- 功能：拼接命令行。串行 `subprocess.run`。
- 输出：`dmeval_cmd.txt` 与 `seed*.log`。

4) 解析/分析层（Adapter + Collect + Objective + Plot）
- Adapter：`dmeval/src/dmeval/adapters/mpd.py`
- Collect：`dmeval/src/dmeval/collect.py`
- Objective：`dmeval/src/dmeval/objective.py`
- Plot：`dmeval/src/dmeval/plotting.py`

---

## 5. 调用链（从一条命令到一堆 CSV）

### 5.1 最常用的一条命令

你一般会用：
- `dmeval run`

它的含义很直接：
- 先跑 Stage I（tune）
- 再跑 Stage II（compare）
- 两段共享同一个 `pipeline.root`

### 5.2 顶层调用链

```
dmeval/src/dmeval/cli.py
  └─ load_hydra_config()        -> 读 config + overrides
  └─ run_tune(cfg)              -> Stage I
  └─ run_compare(cfg)           -> Stage II
```

你想确认 Hydra 是否生效，用：
- `dmeval explain`

它会打印 compose 后的最终配置。

---

## 6. Stage I：tune（调参阶段）怎么跑

话题先说结论：**Stage I 的输出是 `best_patch.yaml`。**  
Stage II 只认它。

### 6.1 Stage I 的内部链路

```
stage_tune.py
  ├─ search.generate_candidates()         -> 生成 candidate 列表
  ├─ runner.run_planner_subprocess()      -> 串行跑 planner
  ├─ adapter.collect_trial_rows()         -> 读产物，变成 trial 行
  ├─ collect.aggregate_mean_std()         -> trial → run → candidate
  └─ objective.select_topk()              -> 过阈值 + 排序，选 best/top-k
```

### 6.2 Candidate 是怎么来的

配置在 `tune.samplers[*].search`。

`strategy: grid`。意思是网格搜索：
- 每个参数写一个离散列表。
- 列表之间做笛卡尔积。

`strategy: random`。意思是随机搜索：
- 你写分布或 choices。
- 工具采样 `n_candidates` 个候选。

实现位置：`dmeval/src/dmeval/search.py`

### 6.3 一个 candidate 会跑几次

一条 candidate，不是跑一次。

Run。它等于 candidate × seed。  
Trial。它是 run 内的 N 次尝试。

所以总执行次数是：
- `#candidate × #seed`

每次执行，MPD 会在结果目录下写 N 个 trial 产物。

### 6.4 Stage I 产物是什么

每个 sampler 目录会有三张表：
- `trial_metrics.csv`：每个 trial 一行
- `run_metrics.csv`：按 seed 聚合。列名是 `*_mean`/`*_std`
- `candidate_metrics.csv`：跨 seed 聚合。Stage I 用它选 best

best 的固化文件：
- `best_configs/<sampler>/best_patch.yaml`：核心
- `best_configs/<sampler>/best.yaml`：辅助检查。它是 base_cfg + patch 的完整 cfg
- `best_configs/<sampler>/topk.yaml`：备查

---

## 7. Stage II：compare（公平对比阶段）怎么跑

话题先说结论：**Stage II 读 `best_patch.yaml`。它对多场景重复评测。**

### 7.1 Stage II 的内部链路

```
stage_compare.py
  ├─ discover samplers from best_configs/
  ├─ for each scenario × sampler:
  │    ├─ merge base_cfg + best_patch
  │    ├─ runner.run_planner_subprocess()
  │    └─ adapter.collect_trial_rows()
  ├─ collect.aggregate_mean_std()         -> trial → run → agg
  ├─ write rank_*.csv
  └─ plotting.plot_stage_compare()        -> 输出 png
```

### 7.2 Stage II 为什么是“公平对比”

公平点在两处：
- sampler 内部。它用 Stage I 找到的 best_patch。
- 场景之间。它对每个 scenario 打同一份 best_patch。

这让你在论文里能说清楚：
- “每个 sampler 用了自己最优的一套配置”
- “所有 sampler 在同一套场景集合上对比”

---

## 8. 数据读取机制（最关键的细节）

话题先说结论：**DMEval 先读 jsonl。没有就读 pt。**

### 8.1 为什么要两条路

jsonl 路。优点：
- 文件轻。读得快。
- 不依赖 torch。

pt 路。优点：
- 不改 MPD 也能跑。
- 字段全。

### 8.2 MPDAdapter 具体读什么

入口函数：
- `MPDAdapter.collect_trial_rows(results_root=...)`

它会在 `results_root` 下递归找：
- `trial_metrics.jsonl`（优先）
- `results_single_plan-*.pt`（回退）
- `args_inference.yaml`（补元信息）

这三类文件的作用：
- `trial_metrics.jsonl`：每行一个 trial 指标。最适合 DMEval。
- `results_single_plan-*.pt`：每个 trial 一个文件。DMEval 用 `torch.load` 抽取 `result.metrics.*` 字段。
- `args_inference.yaml`：MPD 自己写的“本次推理配置快照”。DMEval 用它补 `planner_alg` 与 `diffusion_sampling_method`。

实现位置：
- `dmeval/src/dmeval/adapters/mpd.py`

## 9. “run 内 N 个 trial”怎么处理（你关心的统计意义）

你说的点很对：  
**单条 trial 没意义。平均值才有意义。**

DMEval 的做法很明确：
- 先把每个 trial 抽成一行（trial_df）。
- 再聚合出 run_df（按 seed）。
- 再聚合出 candidate_df（跨 seed）。

Stage I 的聚合键：
- run：`scenario, sampler, candidate_id, run_tag, seed`
- candidate：`scenario, sampler, candidate_id`

Stage II 的聚合键：
- run：`scenario, sampler, run_tag, seed`
- agg：`scenario, sampler, run_tag`

实现位置：
- `dmeval/src/dmeval/collect.py`
- `dmeval/src/dmeval/stage_tune.py`
- `dmeval/src/dmeval/stage_compare.py`

结论：  
**MPD 这种 N-trial 的 run 结构。DMEval 完全兼容。它按平均值做 objective 与排名。**

---

## 10. Hydra 在哪里？它“显式”吗

Hydra 体现点很集中：
- 位置：`dmeval/src/dmeval/config_loader.py`
- 用法：compose API（`initialize_config_dir + compose`）

你能直接看到的表现：
- `-o key=value` 覆盖生效
- `dmeval explain` 打印最终配置

你看不到的表现：
- 没有 `.hydra/` 目录
- 没有自动切 cwd
- 没有 Hydra launcher

原因很简单：这就是 L1 规格。

---

## 11. 可扩展点（你以后写论文“可扩展性”用得上）

### 11.1 新增一个 planner 的适配

你要做的事只在 Adapter 层：
- 新建 `dmeval/src/dmeval/adapters/<new>.py`
- 写一个 `collect_trial_rows()`，输出统一字段口径

主流程不用改。Stage I/II 也不用改。

### 11.2 新增一个搜索策略

你要动的位置很少：
- `dmeval/src/dmeval/search.py`

新增 `strategy: optuna` 时的关键点：
- “一个 candidate 跑完再更新”。
- 不要按单条 trial 更新。

### 11.3 新增一个 objective

你要动的位置：
- `dmeval/src/dmeval/objective.py`

你要改的东西：
- constraints 的规则
- 排序 key 或 score
