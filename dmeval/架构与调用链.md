# DMEval vNext（L1）架构与调用链说明

> 本文档专门回答三件事：  
> 1) **为什么“通用工具”里会出现 `MPDAdapter` 这种 MPD 专用文件**；  
> 2) **整体调用链**（从 CLI 到子进程，再到指标抽取/聚合/排名/绘图）；  
> 3) **每个文件的职责**（你写论文/画架构图时可以直接引用这份说明）。

---

## 1. 为什么需要 Adapter？为什么会有 `MPDAdapter`？

### 1.1 “通用”指的是：流程通用，不是“解析逻辑完全通用”

DMEval 的通用性体现在：
- Stage I/Stage II 的评测流程是通用的（tune → best_configs → compare）
- 产物（trial/run/candidate CSV、rank、plots、manifest）是通用的
- 调参策略（grid/random/optuna）、objective（阈值+排序/评分）是通用的

但**“被测系统的输出格式”不可能天然通用**：
- 不同 planner 会把结果写成 `.pt`/`.npz`/`.jsonl`/数据库/日志……字段名也不同
- 同一个 planner（MPD）也可能在不同版本下产物稍有差异

因此必须有一层隔离：把“读取产物/抽字段”的不稳定部分，和“评测流程/聚合/排名”的稳定部分分开。

这就是 Adapter 层存在的原因。

### 1.2 `MPDAdapter` 的定位：**第一个落地适配器（参考实现）**

按照 `工具描述文档.md` 的 L1 规格：
- L1 首个适配对象是 MPD
- Adapter 需要支持 **优先 jsonl、否则回退 pt**

所以仓库里提供 `dmeval/src/dmeval/adapters/mpd.py`：
- 它只做 MPD 相关的“目录发现/文件读取/字段抽取”
- 其它所有 Stage I/II 的流程代码都不写 MPD 细节

这样做有两个直接好处：
1) **让 DMEval 的主流程保持通用/可复用**：换 planner 时只替换/新增 adapter
2) **把“易变的解析逻辑”集中管理**：未来 MPD 输出变了，只改 `MPDAdapter`，不动 tune/compare 逻辑

> 换句话说：`MPDAdapter` 不是让工具变得“不通用”，恰恰是**为了通用性**而引入的隔离层。

## 2. 总体架构（L1：串行、Hydra 只用于 compose）

核心模块分三层：

1) **配置层（Hydra compose）**  
   - 只负责 defaults 组合与 overrides 覆盖  
   - 不接管 cwd、不创建 Hydra outputs 目录、不启用并行 launcher

2) **管线编排层（Stage I / Stage II）**  
   - Stage I：生成 candidates → 串行跑 planner → 抽取/聚合 → objective 选 best → 写 best_configs  
   - Stage II：读取 best_configs → 对多 scenario 串行跑 planner → 抽取/聚合 → rank/plot

3) **Adapter 层（面向产物目录）**  
   - discover/load/extract（jsonl / pt）  
   - 输出统一字段 dict（trial 级别）

## 3. 调用链（从一条命令到最终 CSV/plots）

以推荐的一条命令为例：

```bash
PYTHONPATH=dmeval/src python -m dmeval.cli --config dmeval/conf/config.yaml run
```

### 3.1 CLI → 配置解析

1) `dmeval/src/dmeval/cli.py`
   - 解析 `--config` 与 `-o/--override`
   - `run` 子命令会顺序执行：`run_tune(cfg)` → `run_compare(cfg)`

2) `dmeval/src/dmeval/config_loader.py`
   - 使用 Hydra **compose API** 读取 YAML
   - 将 defaults 与 overrides 组合成最终 `cfg`

### 3.2 Stage I（tune）内部链路

`dmeval/src/dmeval/stage_tune.py`：

1) 读取 Stage I 配置：scenario/base_cfg、seeds、samplers、search space、objective 等  
2) 对每个 sampler：
   - `dmeval/src/dmeval/search.py` 生成 candidates（grid/random）
   - 对每个 candidate：
     - 生成 `cfg_inference.yaml`（base_cfg + patch 合并）
     - `dmeval/src/dmeval/runner.py` 串行 `subprocess.run(...)` 调用 planner（例如 MPD）
     - `dmeval/src/dmeval/adapters/mpd.py` 从结果目录抽取 trial 行（jsonl 优先，否则 pt）
3) `dmeval/src/dmeval/collect.py`
   - trial → run mean/std
   - trial → candidate mean/std（用于 objective）
4) `dmeval/src/dmeval/objective.py`
   - constraints（阈值）过滤 + lexicographic 排序/score
   - 选择 best/top-k
5) 写出 Stage I 产物：
   - `tune/<sampler>/{trial_metrics.csv, run_metrics.csv, candidate_metrics.csv}`
   - `best_configs/<sampler>/{best_patch.yaml, best.yaml, topk.yaml}`
   - `tune_manifest.yaml`

### 3.3 Stage II（compare）内部链路

`dmeval/src/dmeval/stage_compare.py`：

1) 扫描 `best_configs_root` 得到 samplers  
2) 对每个 scenario × sampler：
   - 读取 `best_patch.yaml`，合并到该 scenario 的 base_cfg
   - `runner.py` 串行跑 planner
   - `MPDAdapter` 抽取 trial 行
3) `collect.py` 聚合：
   - trial → run mean/std（按 seed）
   - trial → agg mean/std（按 scenario,sampler）
4) 生成排名：
   - `rank_success.csv / rank_fraction_valid.csv / rank_path_length.csv / rank_speed.csv`
5) `dmeval/src/dmeval/plotting.py` 输出基础图：
   - success / fraction_valid / time 的柱状图
   - time vs success 散点图
6) 写出 `compare_manifest.yaml`

## 5. 文件职责索引（你要的“每个文件干什么”）

### 5.1 Python 源码（`dmeval/src/dmeval/`）

- `dmeval/src/dmeval/cli.py`：CLI 入口（tune/compare/run/explain）
- `dmeval/src/dmeval/config_loader.py`：Hydra compose 加载配置（不使用 `@hydra.main`）
- `dmeval/src/dmeval/stage_tune.py`：Stage I 编排（候选生成→运行→抽取→聚合→选 best→写 best_configs）
- `dmeval/src/dmeval/stage_compare.py`：Stage II 编排（读 best_configs→多场景运行→聚合→rank→plot）
- `dmeval/src/dmeval/runner.py`：子进程 runner（统一命令行、记录 log/cmd、串行运行）
- `dmeval/src/dmeval/search.py`：candidate 生成（grid/random；optuna 预留）
- `dmeval/src/dmeval/objective.py`：constraints + 排序/评分（输出 top-k/best）
- `dmeval/src/dmeval/collect.py`：trial/run/candidate 聚合与 CSV 写出
- `dmeval/src/dmeval/plotting.py`：基础图输出（matplotlib）
- `dmeval/src/dmeval/util.py`：通用工具函数（yaml/jsonl、merge patch、目录管理等）
- `dmeval/src/dmeval/__main__.py`：允许 `python -m dmeval...`
- `dmeval/src/dmeval/__init__.py`：版本号等

### 5.2 Adapter（`dmeval/src/dmeval/adapters/`）

- `dmeval/src/dmeval/adapters/mpd.py`：MPDAdapter（读 jsonl/pt + args_inference.yaml，抽取规范字段）
- `dmeval/src/dmeval/adapters/__init__.py`：导出 adapter

> 扩展方式：新增 `adapters/<new_planner>.py`，实现同样的 `collect_trial_rows(...)` 输出字段口径即可。

### 5.3 配置（`dmeval/conf/`）

- `dmeval/conf/config.yaml`：默认主配置（示例：DDIM + DPM-Solver++）
- `dmeval/conf/config_dummy_small.yaml`：dummy 最小闭环配置（用于快速自检/单测）
- `dmeval/conf/planner/mpd.yaml`：planner=mpd 的入口/工作目录配置
- `dmeval/conf/planner/dummy.yaml`：planner=dummy 的入口配置
- `dmeval/conf/adapter/mpd.yaml`：adapter=mpd 的文件名/优先级配置
- `dmeval/conf/objective/lexicographic.yaml`：阈值+字典序排序配置

### 5.4 辅助脚本与测试

- `dmeval/scripts/dummy_planner.py`：不依赖 MPD 的自检 planner（写 jsonl，便于验证闭环）
- `dmeval/tests/test_dummy_e2e.py`：最小端到端单测（tune→compare→检查 CSV/plots 是否生成）

## 6. 你在论文里怎么“讲通用性”（可直接转述）

可以用一句话概括：

> DMEval 的通用性来自 **“稳定的评测流程” 与 “可替换的 Adapter”** 的解耦：  
> 评测管线（tune/compare、聚合、目标函数、产物契约）保持稳定；  
> 针对不同 planner 的输出差异，仅通过新增/替换 Adapter 来适配。
