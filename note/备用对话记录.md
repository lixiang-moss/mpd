一、重复运行与数据聚合：到底在做什么，为什么这么做
1）什么叫“同一组配置”
一组配置 = 一个固定的三元组：

* 场景 scenario（例如某个 env_id / 某个 yaml 场景文件）
* 采样器 sampler（DDIM / DPM-Solver++ / …）
* 采样器推理超参 params（steps、order、guide_weight、t_start…等）
  这三个固定不变。
  2）为什么要跑 n 次（你说 n=50）
  因为 MPD 每次推理的“上下文”是随机的（你说的起点/终点/末端目标等随机生成），而且扩散采样本身也可能有随机性。只跑一次，会被“运气好/运气差的那个上下文”强烈影响，结论不稳。跑 n 次相当于：
* success：从“这一次成不成”变成“在随机上下文分布上成功概率≈多少”
* fraction_valid：从“这一次有效率多少”变成“平均有效率、波动多大”
* path_length/smoothness/error：从“这一次轨迹质量”变成“期望质量+稳定性”
  3）每次运行你要记录什么（强烈建议“原始记录全保留”）
  每跑一次（同配置下的第 k 次），你至少记录两类信息：
  A. 标识信息（用于之后能分组聚合）
* experiment_id：这组配置的唯一ID（建议对“scenario+sampler+params”的规范化JSON做hash）
* run_id：第几次运行（0…n-1）
* seed：如果 MPD 支持/你加了最小改动支持随机种子，就记录 seed（否则也记录一个你这边的seed并传给MPD）
* context_id：本次随机上下文的ID（如果 MPD 能返回/保存 start/goal 索引或pose，就记录索引；不行就记录“第k次抽样”）
  B. 指标信息（你给的示例那套，直接照抄字段）
* t_inference_total, t_generator, t_guide
* trajs_all: success, success_no_joint_limits_vel_acc, fraction_valid, fraction_valid_no_joint_limits_vel_acc, collision_intensity, ee_pose_goal_error_* mean/std
* trajs_valid: diversity, ee_pose_goal_error_* mean/std, path_length_mean/std, smoothness_mean/std
* trajs_best: ee_pose_goal_error_position_norm, ee_pose_goal_error_orientation_norm, path_length, smoothness
  重要：**每一次运行都把这些指标作为“一行”写入总表（raw table）**，不要只保留最后的均值。原因是：
* 你以后想换聚合方法（median、trimmed mean、分位数、置信区间）不用重跑
* 可以做异常值诊断（某些上下文特别难导致指标爆炸）
* 对“MPD以外的框架”，它可能“跑一次就代表性足够”，那 raw table 仍然兼容（n=1也能聚合）
  4）聚合到底怎么做（跑完 n 次后做 group-by）
  你建议“跑完后统一聚合”是对的：通用且工程上干净。具体聚合规则建议如下：
* 分组键：experiment_id（或 scenario+sampler+params 的组合键）
* 对 success（0/1）：

  * mean = 成功率（success_rate）
  * std = 波动（可选）
  * 也可以输出 sum_success = 成功次数，n_runs = 运行次数（统计更直观）
* 对 fraction_valid / collision_intensity / 各种误差 / path_length / smoothness：

  * 输出 mean、std（至少要 mean；std很有价值，用于稳定性）
  * 如果你担心长尾：再加 median、p25、p75（可选，但很实用）
* 对可能缺失的指标（比如没有 valid traj 时 trajs_valid 相关字段可能不存在）：

  * raw table 里写 NaN
  * 聚合时用“跳过 NaN 的均值/方差”并同时输出 valid_count（告诉你这个指标在 n 次里有多少次可用）
    产物建议两个文件：
* raw_runs.csv（每次运行一行，永不覆盖）
* agg_by_config.csv（每组配置一行，聚合后的 mean/std/median 等）

明白了：**n 次是在 MPD 的 `inferences.py`（你写的 infereces.py）内部循环完成**，评测框架对同一配置**只调用一次 MPD**，然后从这一次运行里拿到 **n 条结果**。我之前把“n 次循环”放到了评测框架里，这是错的。下面是纠正后的落地做法（框架怎么做、要从 MPD 拿什么、对调参/对比有什么影响）。

## 1）正确的执行粒度

* **评测框架的最小执行单元**：一次子进程调用 MPD（给定 scenario+sampler+params 的配置）。
* **MPD 一次运行的产出**：内部循环 n 次，得到 n 份 metrics（每个上下文一份）。
* 所以：框架不再做“for run_id in range(n)”循环；**框架只做“for config in configs”循环**。

## 2）框架如何记录 raw 表（依然是“一次上下文一行”）

你原先的想法“每次实验结果都放总表”仍然成立，只是来源变了：

* 以前：框架每次调用 MPD 得到 1 条 → 追加 1 行
* 现在：框架每次调用 MPD 得到 n 条 → 追加 n 行
  关键变化：**框架要能从一次 MPD 运行中提取 n 份 metrics**，并给它们标上 run_id/context_id。

### 你需要 MPD 满足/暴露的东西（让 Codex 去 repo 里确认并实现“最小改造”）

最稳的方式：MPD 每次内部循环保存一个结构化结果（或至少一个 JSON 行）。两种主方案：
A）**结构化文件（推荐）**

* MPD 在每次内部运行 k 时，写一个 `results_single_plan-{k:03d}.pt` 或 `results_single_plan-{k:03d}.json` 到你指定的 `output_dir`。
* 框架运行结束后，直接遍历 output_dir 里这 n 个文件，逐个读出 metrics → 写入 raw_runs.csv（n 行）。
  B）**stdout 多段输出（可用但脆弱）**
* MPD 每次内部运行 k 打印一段固定格式 metrics（最好一行 JSON），并明确带 `run_id=k`。
* 框架捕获 stdout，按 run_id 切分出 n 份 → 写 raw 表。
  我强烈建议 A 或 “stdout 输出 JSON 行” 的 B（不是 pprint 文本），因为 **pprint 的格式一变解析就炸**。

## 3）聚合仍然在框架做（只是不再“每配置跑完 n 次后聚合”，而是“读完 n 条后聚合”）

聚合逻辑不变：

* raw_runs.csv：每条上下文一行（共：configs 数量 × n 行）
* agg_by_config.csv：按 experiment_id（=scenario+sampler+params）分组统计 mean/std/median…
  区别仅在于：raw 的 n 行来自“同一次 MPD 运行的 n 次内部循环”，而不是框架多次调用。

## 4）对调参/对比流程的影响（你需要知道的“后果”）

因为一次评估（一个参数组合）就会触发 MPD 内部跑 n 次：

* **单个 trial 成本更高**（但统计更扎实）
* **早停更难做**：如果你想省时间，最好在 MPD 内部支持“跑到一半发现 success 太低就提前停”（这是 MPD 侧优化；框架侧做不了，因为框架只看到整个子进程结束后的结果）。
  如果你不想改 MPD：那调参策略就要偏“预算友好”：
* 离散少量选项：小枚举没问题
* 连续参数：Optuna/TPE 也行，但 trial 数要控制（比如 20~60），否则每个 trial 都要跑 n 次会非常慢
