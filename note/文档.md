



# 评估结果聚合脚本——设计文档

## 概述

本文档描述了一个由 AI 代码助手（Codex）生成的 Python 脚本，用于自动化评估运动规划算法。目标是在不同随机条件（起点/终点状态）下多次运行给定的推理程序，以保证统计公平性，然后对性能指标进行汇总。该脚本不会实现规划算法本身；相反，它会调用一个现有的推理函数（来自 MPD 库），该函数在内部处理多次运行。本评估框架的重点是数据收集与统计分析，确保每个算法配置都被公平测试，并对结果进行全面汇总。

## 运行推理实验

### 1. 一次调用、多次运行的执行方式

评估脚本将利用现有的 inference.py 程序（来自 MPD）在一次执行中完成多次规划试验。我们不会在外部框架中循环重复试验；相反，我们依赖 inference 代码内置的能力：一次调用即可运行 n 个不同的起点-终点场景。在 MPD 的 inference.py 中，这通常由某个参数控制（例如 n_start_goal_states），其默认值为 1，但可设置为更大，以在同一配置下使用不同随机起点/终点对运行多次。评估脚本假设推理配置（YAML 或命令行参数）中已指定所需的试验次数。该做法通过在大量随机测试中保持算法配置一致来确保公平性，并将多次运行的逻辑集中在 inference 代码内部（框架无需管理循环）。

### 2. 触发推理运行

对每个要评估的算法或配置，脚本将以合适参数调用一次推理程序：

* 配置选择：脚本应接受配置文件列表，或为每种算法变体提供预定义的参数集合。对每个配置，它会生成一个唯一标识符（run tag）用于标注该实验的结果。
* 结果目录：为每次运行提供专用输出目录。例如，结果可组织在统一的 results_root 目录下，并为每个 run tag 建立子文件夹。若测试多个算法或参数集合，每个都使用独立子文件夹。脚本会构造类似 results_root/<run_tag> 的结果路径（如有需要，还可为不同 seed 或 trials 增加更深层子目录；但本设计中一次运行内部已覆盖多次试验，因此单次 run 即可包含多个 trial）。这确保不同配置的输出不会混在一起。
* 调用方式：使用 Python 的 subprocess 或类似机制，脚本调用推理程序（例如 python3 inference.py），并传入适当参数：

  * --cfg_inference_path <config_file>：指向该算法的 YAML 配置；
  * --results_dir <results_root/run_tag/optional_seed>：指定输出保存位置；
  * --seed <value>：用于随机选择的可复现性（如有需要；例如设置随机起始状态选择的基准 seed）。seed 可固定或随配置变化；但由于每次 inference 运行内部已覆盖多次随机试验，为一致性可使用常量 seed，除非另有明确需求；
  * 其他必要标志（例如启用低内存模式，以便每次试验只存最少数据）。
    每次调用都会以给定算法配置执行推理，并在内部自动循环 n 个随机场景（会打印类似 “PLANNING i/n” 的进度）。评估框架无需实现外层重复试验循环——它只对每个配置调用一次 inference，让 inference 内部完成 n 次运行。

### 3. 无需外部控制 n

关键点：框架不会在外部设置或控制试验次数。我们假设试验次数 n 已在 inference 的 YAML 或默认设置中配置。这避免了重复配置，并让评估代码专注于编排实验与收集结果。总之：对每个算法配置，脚本只调用一次 inference.py，而 inference.py 会在内部运行指定数量的规划尝试。该设计保证每个配置的试验执行方式公平且一致。

### 4. 多配置（可选）

若要评估多个算法或参数集合，脚本将遍历所有提供的配置：

* 对每个配置，确保结果输出路径唯一（例如将算法名或参数编码进 run_tag）；
* 按上述方式调用 inference；
* 等待该次运行完成后再进行下一次（必要时可避免资源竞争，因为这些运行可能使用 GPU / IsaacGym）。
  最终，results_root 目录将包含每个 run_tag 的子目录，每个子目录中包含该配置的多次运行结果文件。

## 数据收集与指标聚合

所有推理运行完成后，脚本将从输出文件中收集并汇总结果。MPD inference 会为每次运行生成一组结果文件与配置记录：

* 每个试验（一个起点-终点场景）会生成一个文件（以 PyTorch 的 .pt 保存），文件名模式为 results_single_plan-XXX.pt，其中 XXX 是索引（例如 000、001、……）。这些文件包含序列化的结果对象（例如 DotMap），其中包含该试验的指标与细节。
* 结果目录中还会保存 args_inference.yaml，用于记录该次运行使用的配置与参数（包括算法设置，如规划器类型、采样方法等）。
  评估脚本将执行以下聚合步骤：

### 1. 定位结果文件

遍历 results_root 目录树以查找所有结果文件。具体而言，搜索所有文件名以 "results_single_plan-" 开头且以 .pt 结尾的文件。每个文件对应某个配置的一次试验。收集这些文件即可获得所有运行、所有配置的数据。

### 2. 识别运行上下文

对每个找到的结果文件，确定其所属配置与试验：

* 路径结构提供上下文信息。例如，若结果保存在 results_root/<run_tag>/<seed>/results_single_plan-000.pt，则脚本可解析路径得到 run_tag（实验标识符）与 seed（如果存在 seed 子目录）。
* 若不使用 seed 子目录（文件直接位于 run_tag 文件夹下），脚本可将 run_tag 视为唯一实验 ID，并将 seed 记为固定值或留空/常量（因为试验已在内部完成）。
* 通过目录名提取 run_tag（用于按配置分组汇总）与 seed（或试验集标识，用于区分同配置下的重复运行）。

### 3. 加载并提取指标

对每个结果文件：

* 使用 torch.load(<file_path>) 加载 PyTorch 对象，得到一个结果对象（可能是 DotMap 或类似结构），包含该试验的各项属性。
* 从结果对象中提取 metrics。在 MPD 中，每次试验后会保存一个 metrics 对象（例如 results_single_plan.metrics），其中包含性能度量。典型指标包括：

  * 成功率：规划器是否找到有效路径（例如 metrics.trajs_all.success，成功为 1，失败为 0）；
  * 有效轨迹比例：生成轨迹中有效（无碰撞等）的比例，例如 fraction_valid；
  * 路径质量指标：例如最佳轨迹的路径长度（path_length）与平滑度（smoothness）；
  * 目标误差：例如最佳轨迹末端执行器位置/姿态误差（ee_pose_goal_error_*）；
  * 计时信息：总推理时间、生成器时间、引导时间（t_inference_total、t_generator、t_guide）；
  * 忽略约束下的成功：例如 success_no_joint_limits_vel_acc 及对应的有效比例（忽略某些约束）；
  * 碰撞强度：衡量轨迹中碰撞严重程度的指标（如果定义了）。
    脚本应尽可能提取所有可用且相关的指标。它可通过属性访问或字典键获取值；若结构嵌套（例如 metrics 可能包含 trajs_all、trajs_best、trajs_valid 等子字段表示不同轨迹子集），脚本将按层级导航提取（例如 success 位于 metrics.trajs_all.success）。
* 配置参数：此外，脚本会打开并读取对应结果目录中的 args_inference.yaml（若存在），以获取应记录的配置参数：

  * 环境或场景标识（例如是否使用了某种环境变体）。在 MPD 中，args YAML 里的 env_id_replace 指示环境是否被替换/修改；脚本可将其作为上下文写入结果；
  * 算法名或规划器标识（planner_alg）；
  * 扩散采样方法或其他方法细节（diffusion_sampling_method）；
  * 其他可区分配置的关键参数（如步数、阶数等，若对 sweep 有意义）。
* 动态判定：若某些上下文标签（如场景名）未显式存储，脚本将推导。例如，MPD 自带的收集脚本会推断场景标签：如果 env_id_replace 被设置（且不为 “false/none”），则标为 "scene02"；否则标为 "scene01"。我们的脚本应实现类似逻辑，为每条结果打上合适的场景标签以便理解。

### 4. 缺失数据处理

某些指标在部分试验中可能缺失或不适用（例如没有找到有效轨迹时，某些值可能为 None）。脚本必须能稳健处理：

* 若属性缺失或为 None，则赋占位符（数值用 NaN）。参考脚本中使用辅助函数将 None 转为 float("nan")；我们也采用相同方式，以避免错误并表示数据缺失。
* 保证类型一致：将张量或复杂类型转换为可写入 CSV 的基础类型。例如若指标值是 PyTorch tensor，则需要 detach 并转换为 float；布尔值可转为 0/1 或 True/False 字符串等。
* 使用安全访问方式避免 KeyError/AttributeError：例如用 getattr 并提供默认值来访问嵌套属性（如 MPD 脚本所示），或在字典中先检查键是否存在。这样即使字段不存在，也会返回默认值（空字符串或 NaN）。

### 5. 聚合为数据行

对每个加载的试验文件，构造一行数据（字典或值列表），包含：

* 标识信息：scenario（例如按逻辑推断出的 scene01/scene02）、env_id_replace（若表示环境变化的字段存在）、run_tag（该算法/配置的标识）、seed（试验索引或 seed 值）、result_file（结果文件名，便于追溯）。
* 指标：上述提取的所有指标值（成功率、有效比例、误差、时间等）。
* 配置信息：planner_alg、diffusion_sampling_method 或其他会在不同运行间变化的关键参数。
  该行稍后会写入 CSV 中作为一行记录；列名对应这些字段的 key。

## 输出格式

处理完所有结果文件后，脚本将生成汇总输出，主要为 CSV（逗号分隔值）格式，便于分析：

### 聚合指标 CSV

在 results_root 目录下写出一个文件（例如 sweep_metrics.csv），每个试验一行。包含表头（列名），例如：

* scenario, env_id_replace, run_tag, seed, result_file,
* success, success_no_joint_limits_vel_acc,
* fraction_valid, fraction_valid_no_joint_limits_vel_acc,
* collision_intensity,
* ee_pose_goal_error_position_norm_best, ee_pose_goal_error_orientation_norm_best,
* ee_pose_goal_error_position_norm_mean_all, ee_pose_goal_error_position_norm_std_all,
* ee_pose_goal_error_orientation_norm_mean_all, ee_pose_goal_error_orientation_norm_std_all,
* ee_pose_goal_error_position_norm_mean_valid, ee_pose_goal_error_position_norm_std_valid,
* ee_pose_goal_error_orientation_norm_mean_valid, ee_pose_goal_error_orientation_norm_std_valid,
* path_length_best, path_length_valid_mean,
* smoothness_best,
* t_inference_total, t_generator, t_guide,
* diffusion_sampling_method, planner_alg。
  后续每行填入该试验对应的值。（具体指标集合可按需调整，但至少应涵盖成功率、有效性、路径长度、时间，以及主要性能判据。）

### 排名结果（可选）

可选地，脚本可生成额外 CSV，用某些指标对配置进行排序。参考脚本做法，可按以下方式排序聚合数据：

* 成功率（降序），再按最快时间（升序），以观察在成功与速度上表现最佳的配置；
* 有效轨迹比例（降序），再按时间；
* 最短路径（升序）；
* 最快推理时间（升序）。
  对每种排序写出一个 CSV（例如 sweep_rank_success.csv、sweep_rank_fraction_valid.csv 等），列相同但行顺序按排名排列。这有助于快速比较关键指标下的配置表现。若只评估一个配置，则不必生成排名文件。

### 控制台输出

脚本还应在控制台打印摘要信息告知用户：

* 找到并处理了多少个结果文件；若未找到任何结果，则打印提示；
* 确认 CSV 输出位置（例如 “Wrote sweep_metrics.csv” 及排名文件路径）；
* 如有需要，可打印一些快速统计（例如每个配置的总体成功率等）以便查看，但详细分析应通过 CSV 完成。
  所有输出文件都写在指定的 results_root（或其子目录）下，方便用户定位评估汇总结果。

## 实现说明

### 语言与库

脚本使用 Python 编写，使用 PyTorch 加载 .pt 文件（torch.load），可能使用 NumPy 做数值操作，使用 yaml 库解析 YAML 配置文件（args_inference.yaml）。脚本顶部应导入所需模块（例如 os、csv、yaml、torch 等）。

### 鲁棒性

脚本需处理异常情况，例如：

* 文件读取错误：若某结果文件损坏或无法加载，应捕获异常、打印警告并跳过该文件，而不是使整个脚本崩溃；
* 目录或文件缺失：若找不到预期的结果目录或文件，应给出清晰提示。

### 参数化

脚本可支持命令行参数，例如：

* --configs：配置文件路径列表，或包含多个配置的目录；
* --results_root：所有结果与输出 CSV 的根目录；
* 可选标志如 --collect_only：跳过运行推理，仅对现有结果进行聚合（便于对历史结果重复聚合）。
  但如果不需要，也可更简单：让用户在脚本中直接编辑配置列表并运行。

### 复用已有功能

我们将镜像 MPD 内部收集指标脚本的部分功能。例如，实现类似 _to_float 的辅助函数安全地将值转换为 float，或类似 _safe_get 的安全访问函数，会让代码更清晰。可以直接吸收 MPD 的 collect_sweep_metrics.py 中的类似逻辑。

### Codex 的自主实现空间

部分实现细节由代码生成自行决定，只要遵循本指南。例如：

* 循环结构与数据结构（如 rows 列表等）可由 Codex 选择最清晰的写法；
* 场景名推断与边界情况处理：本文档已给出目标行为（如依据 env_id_replace 判定），代码助手据此实现条件与字符串处理；
* 若某些指标或键名有差异，脚本可通过自省（检查 metrics 对象的键/字段）来捕获所有相关字段，而不是把所有可能指标硬编码。这样更具前向兼容性：即使未来新增指标，也能更容易纳入（可以将已知字段写入表头，或动态加入所有发现的数值字段）。总原则是：记录所有重要性能指标，避免人工遗漏。

### 关注点分离

评估脚本只负责“编排运行与聚合”。它假设规划器执行与指标计算由 inference 程序完成。因此脚本不会改变规划器行为，也不会改变其内部运行多少次试验（除了传入配置文件）。它只确保每个配置被运行，并收集其输出结果。这使设计模块化，并与现有代码结构保持一致。
按照该设计，生成的脚本将实现运动规划配置的自动化、公平评估：每个配置利用内部多次随机场景运行机制完成多次试验，并生成全面的 CSV 汇总。研究人员或工程师可据此在统计意义上公平比较不同算法配置的表现，从而满足公平基准测试的要求。
