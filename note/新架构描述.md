# 新架构描述：DMEval（面向 MPD 的两阶段采样器评测工具 vNext）

> 目标：把“扩散采样器（DDPM/DDIM/DPM-Solver++/UniPC…）在机械臂运动规划中的速度–质量权衡”做成**可复现、可扩展、可公平比较**的一套评测工具链。  
> 约束：**只做串行**（不引入复杂并行）；评测工具**不重算指标**，指标由被测模型（例如 MPD）内部计算，DMEval 只负责**提取/聚合/比较/可视化**。

本文档基于：
- 现有 DMEval 实现（`mpd-splines-public/dmeval/`）
- `架构描述.md`、`proposal01.md`、`piepline.md`
- `tu_berlin_kickoff_zh.md` 中的研究问题、两阶段范式、指标维度与“阈值+优化”调参思想
- 我们上面的对话中暴露的真实痛点（Hydra 看不见、grid/seed/trial 概念混乱、想复用 sweep.py 思路但又要通用化）

> 结论先说：你需要的 DMEval 不是“再写一堆 sweep.py”，而是一个**把 sweep 的流程抽象成稳定管线**的工具；同时它也不应该为了“通用”而变得难用，所以 vNext 需要把“概念、配置、输出契约、可解释性”做扎实。

---
## 0. 你现在真正需要的是什么（从疑问反推需求）

从对话里你的困惑可以归纳为 6 类“必须解决的产品需求”：

1) **可解释性（Explainability）**  
你需要随时能回答：“DMEval 这次到底跑了哪些配置？每个配置对应哪些 MPD 参数？输出写到哪？”  
→ 需要“可打印的最终配置”“可打印的实验计划（plan）”“清晰术语表”。

2) **配置体验（Hydra 的合理使用）**  
你希望 Hydra 管理配置组合/覆盖，但不希望 Hydra 偷偷改 cwd、生成奇怪的 outputs 目录导致路径错乱。  
→ Hydra 应该用于“配置组合器”，而不是强行接管运行目录；同时要明确是否要把 Hydra 引入 MPD。

3) **调参能力（搜索策略可扩展）**  
你现在先用网格搜索，但未来要能上随机/贝叶斯；且 dpm_solver 一类参数空间天然适合“coarse→refine”。  
→ 需要 `SearchStrategy` 插件层：grid/random/optuna；MPD 专用 two-stage 作为可选策略。

4) **公平性（seed / 数据集抽样 / 统计口径）**  
你必须能保证不同采样器在相同 seed 下评测的是同一批 start-goal，并按统一口径聚合统计。  
→ 需要对 seed/run/trial 的定义固定下来，并在产物中记录清楚。

5) **结果契约（不想依赖 sweep 文件、也不想 DMEval 重算指标）**  
你希望 DMEval 只提取，但又不想被 `.pt` 绑死（需要 torch、文件大）。  
→ 需要一份“最小结果契约”：planner 侧输出 `metrics.jsonl`（或同等格式），DMEval 直接读它；`.pt` 作为可选附件。

6) **两阶段范式落地（Stage I 输出 best；Stage II 用 best 跨场景对比）**  
这来自 proposal/tu_berlin 文档，是你整篇工作可信度的核心。  
→ 需要标准化的 `best_configs/` 产物与可复现实验记录。

## 1. 关键术语（必须统一，否则永远讲不清）

下面这些词在你的项目里经常被混用；vNext 必须在文档、日志、输出文件里强制一致：

### 1.1 实验对象
- **Scenario（场景）**：要评测的环境/任务配置（在 MPD 里体现为一个 base inference YAML，例如 `config_EnvSpheres3D-RobotPanda_00.yaml`）。
- **Sampler（采样器）**：DDPM / DDIM / DPM-Solver / DPM-Solver++ / UniPC…（在 MPD 里通常由 `diffusion_sampling_method` + 一段 sampler 专用参数块决定）。

### 1.2 运行层级（从粗到细）
- **Candidate（候选配置）**：一组“可调超参”的具体取值（例如 `dpm_solver_steps=60, order=2, prior_weight=1.5`）。  
  候选配置会有一个稳定的标识：`candidate_id` 或 `run_tag`。
- **Run（一次运行）**：对某个 `candidate_id`、在某个 `seed` 下，调用一次 MPD inference（会产生一批输出文件）。  
  你可以认为：`run = candidate × seed`。
- **Trial（一次规划尝试）**：MPD 在一次 run 内会评测多个 start-goal（由 `n_start_goal_states=N` 决定）。每个 start-goal 对应一个 trial。  
  在 MPD 当前实现里，通常就是一个 `results_single_plan-XXX.*`（`.pt` 或未来的 `.jsonl` 中的一行）。

### 1.3 Seed（随机种子）
Seed 的作用不是“编号”，而是：
- 固定伪随机序列 → **可复现**；
- 固定评测样本抽样（start-goal 抽取）→ **公平比较**（不同 sampler 用同一组 seeds，就更像在同一批题目上考试）。

> 你以后给导师解释时可以一句话：  
> “我们用多 seed 重复运行来降低随机性；并且所有 sampler 用同一组 seeds，从而在同一批 start-goal 上公平比较。”

## 2. vNext 总体工作流（两阶段范式 + 串行）

### 2.1 总流程图（用户视角：你要做什么）

```
你准备/修改配置（Hydra YAML）
  ├─ 选 planner / scenario / objective（defaults）
  ├─ 定义调参策略与搜索空间（Stage I）
  └─ 定义对比场景集合（Stage II）
            │
            v
Stage I: 先调参（单场景）
  1) 生成候选（candidate）列表
  2) 串行跑 MPD：candidate × seeds
  3) 收集 trial -> 聚合成 run 统计
  4) 目标函数：阈值过滤 + 复合评分
  5) 输出每个 sampler 的 best_config（+ top-k）
            │
            v
Stage II: 再公平对比（多场景）
  1) 读取每个 sampler 的 best_config
  2) 在多个 scenario 上串行跑：sampler × scenario × seeds
  3) 统一聚合统计、生成对比表与图
```

### 2.2 系统架构图（组件视角：谁负责什么）

```
                 ┌────────────────────────────┐
                 │         DMEval CLI         │
                 │ tune / compare / collect   │
                 └──────────────┬─────────────┘
                                │
                                v
┌─────────────────────────────────────────────────────────────┐
│  Config Layer（Hydra only for composition/override）         │
│  - 组合 defaults（scenario/planner/objective）               │
│  - 解析 overrides（--override key=value）                    │
└──────────────┬──────────────────────────────────────────────┘
               │
               v
┌─────────────────────────────────────────────────────────────┐
│  Pipeline Orchestrator                                       │
│  - Stage I: SearchStrategy -> CandidateGenerator             │
│  - Runner（串行调用 planner）                                │
│  - Collector（读取产物 -> trial表 -> run表）                 │
│  - Objective（阈值+评分 -> best/topk）                       │
│  - Stage II: BestLoader + ScenarioExpander + Runner+Collect  │
└──────────────┬──────────────────────────────────────────────┘
               │
               v
┌─────────────────────────────────────────────────────────────┐
│  Adapter Layer（与 planner 解耦的关键）                       │
│  - PlannerRunner: “怎么调用 MPD/EDMP/…”                       │
│  - ArtifactAdapter: “怎么从产物提取指标字段”                   │
└──────────────┬──────────────────────────────────────────────┘
               │
               v

       │   MPD（被测）     │
       │  compute metrics  │
       └──────────────────┘
```

## 3. Hydra：在 vNext 中“应该怎么用、用到什么程度”

### 3.1 推荐定位：Hydra 作为“配置组合器”，不是“运行调度器”

你现在最需要 Hydra 提供的能力是：
- `defaults`：把 `scenario/planner/objective` 组合成最终配置
- `--override`：临时覆盖参数（device、seeds、N、某个搜索空间等）

而你**不需要** Hydra 接管的能力是：
- 自动切换 cwd 到 `outputs/...`
- 自动创建 `.hydra/` 目录体系
- 使用 Hydra launcher 并行发射任务

原因：你项目里相对路径很多（MPD 的默认 cfg 路径、results_dir、各种脚本路径），Hydra 的 “chdir + outputs” 机制会让路径理解变难，也会让你更难解释输出在哪。

### 3.2 两种集成方案（你可以二选一；vNext 默认推荐 A）

#### 方案 A（推荐，通用性更强）：Hydra 只在 DMEval（不改 MPD）
- DMEval 用 Hydra compose 得到“评测配置”
- DMEval 仍然给 MPD 传 `--cfg_inference_path <某个YAML文件>`
- DMEval 的 `best_configs/` 存“MPD inference YAML”或“patch YAML”

优点：
- 对 MPD 改动为 0（符合“评测工具不侵入 planner”）
- 以后换 EDMP/其它模型，只需要新增 adapter/runner

缺点：
- DMEval 会生成一些“候选 MPD YAML 文件”（你会看到 generated_configs）

#### 方案 B（可选，体验更像 sweep.py）：MPD 也使用 `@hydra.main`
你允许做轻量级改动：MPD 的 inference 入口变成 Hydra app，并且：
- `hydra.job.chdir=False`（禁止自动切 cwd）
- `hydra.run.dir`（或你自己的参数）指向你希望的 results_root
- 产物路径由你显式指定（避免写到 outputs 里）

此时 DMEval 的 `best_configs/` 就可以存成：
- `best_overrides.yaml`（一组 key=value），而不是生成 YAML 文件

优点：
- 超参以 overrides 形式表达，更轻、更接近你原 sweep.py 的“命令行改参数”
- MPD 内部也能享受 config group 的组织

缺点：
- DMEval 与 MPD 的 config key 体系耦合更强
- 未来换 planner 时迁移成本更高

> vNext 建议：先走方案 A 把论文/导师展示跑通；若后续你明确只服务 MPD 再考虑方案 B。

## 4. 调参（Stage I）在 vNext 的理想形态

`tu_berlin_kickoff_zh.md` 提到的“阈值+优化”范式，在 vNext 里应被显式建模为：

### 4.1 Objective = Constraints + Score

- **Constraints（可行性阈值）**：例如  
  `success_mean >= 0.8`、`fraction_valid_mean >= 0.6`、`collision_intensity_mean <= 0.05`  
  不满足直接淘汰（不参与“最佳”竞争）
- **Score（排序/选择）**：在满足阈值后，用复合评分排序  
  例如：  
  `score = success_mean - α*time_mean - β*collision_mean - γ*path_length_mean - ...`

> 注意：阈值与权重应当**可配置**，不要写死在代码里；否则你后续改统计口径会很痛苦。

### 4.2 SearchStrategy：从“只支持 grid”升级为可插拔

vNext 的 SearchStrategy 接口应当统一成：
- 输入：search_space（参数空间）、budget（最大试验次数）、seed（搜索器自身随机种子）
- 输出：一个候选序列（可能是先生成全量，也可能是动态提出）

至少支持 3 类：

1) **Grid（当前已有）**  
`grid: {key: [v1, v2, ...]}` → 笛卡尔积

2) **Random（建议补齐）**  
需要支持“范围/分布”表示，例如：  
`uniform(0.8, 2.0)`、`loguniform(1e-4, 1e-1)`、`categorical([...])`

3) **Bayesian（建议用 Optuna）**  
由优化器根据历史结果动态提出下一组参数（串行也能跑）

### 4.3 “coarse→refine”两阶段调参（MPD/dpm_solver 很适合）

你原 sweep.py 的经验可以保留，但不要把它写死成“只有 MPD 能用”。更好的抽象是：

- `TwoStageStrategy`
  - Stage A（coarse）：扫离散/结构性参数（steps/order/continuous_time/method）
  - Stage B（refine）：在 coarse top-k 附近，对连续参数（prior_weight/guide_lr/max_perturb_x…）做 random/bayes

这样你既能复用“MPD 的经验”，又不会破坏 DMEval 的通用框架。

## 5. 结果契约（让 DMEval 真正“只提取”，同时不被 `.pt` 绑死）

### 5.1 现状（可以工作，但门槛高）
MPD 当前的典型产物是：
- `args_inference.yaml`
- `results_single_plan-XXX.pt`（包含 metrics）

问题：
- `.pt` 需要 `torch.load`（DMEval 依赖 torch）
- 文件可能很大（虽然 MPD 有 low_mem 模式）

### 5.2 vNext 推荐的“最小产物契约”（对 MPD 的轻量级改动点）

**建议在 MPD inference 里额外写一个“轻量指标侧车文件”**（不改变算法，仅改变输出）：

```
<results_dir>/
  args_inference.yaml
  trial_metrics.jsonl        # 每个 trial 一行 JSON（只含指标与少量元信息）
  run_summary.yaml           # 本 run 的汇总信息（可选）
  results_single_plan-XXX.pt # 可选：需要保存轨迹时再写
```

这样 DMEval 的 MPD adapter 就可以优先读 `trial_metrics.jsonl`：
- 不需要 torch
- 更容易跨模型对接（EDMP 也能输出 jsonl）
- 更符合“评测工具不重算指标”的原则：指标仍由 MPD 计算，只是输出格式更评测友好

> 这类改动属于“轻量级改动”：不触碰 MPD 的核心推理逻辑，只增加一个落盘格式。  
> 如果你坚持 MPD 完全不改，则继续沿用 `.pt` 也可以，但会牺牲一部分通用性与易用性。

## 6. 存储布局（让导师一看就懂，也方便你复现实验）

建议统一输出到 `pipeline_root/`，并固定两阶段目录：

```
pipeline_root/
  stage1_tune/<scenario_name>/
    <candidate_id>/               # 每个候选一个目录（或由 run_tag 命名）
      <seed>/
        args_inference.yaml
        trial_metrics.jsonl (or .pt files)
    _dmeval/
      trial_metrics.csv
      run_metrics.csv
      best_configs/
        <sampler>/
          best_config.yaml        # 或 best_overrides.yaml
          best_patch.yaml
          topk.yaml
      tune_manifest.yaml

  stage2_compare/
    <scenario_name>/<sampler>/
      <seed>/
        args_inference.yaml
        trial_metrics.jsonl (or .pt files)
    _dmeval/
      trial_metrics.csv
      run_metrics.csv
      rank_*.csv
      plots/
      compare_manifest.yaml
```

核心原则：
- **先聚合再分析**：trial → run（mean/std）→ rank/plots  
- **best_configs 单独放**：便于 Stage II 复用与论文复现

## 7. 模块化输入/输出：以 MPD 为例（你实际要提供什么？DMEval 怎么交互？）

### 7.1 你需要给 DMEval 的输入（最低集合）

1) **DMEval 配置（Hydra YAML）**：  
包含：
- 选用的 `scenario/planner/objective`
- Stage I 的 sampler 搜索空间（grid/random/bayes）
- Stage II 的对比场景集合
- seeds、n_start_goal_states、device 等共用运行参数

2) **MPD base inference YAML（每个场景一份）**：  
例如：`mpd-splines-public/scripts/inference/cfgs/config_EnvSpheres3D-RobotPanda_00.yaml`

3) **可运行的 MPD 环境**：  
能在 docker/conda 里正常运行 `scripts/inference/inference.py`

### 7.2 DMEval 与 MPD 的交互（方案 A，不改 MPD）

对每个 candidate×seed，DMEval 执行一次：

```
python mpd-splines-public/scripts/inference/inference.py \
  --cfg_inference_path <generated_cfg.yaml> \
  --results_dir <pipeline_root/.../candidate_id> \
  --seed <seed> \
  --selection_start_goal validation \
  --n_start_goal_states <N> \
  --device cuda:0 \
  ...
```

然后 DMEval 扫描 `<results_dir>` 下的 trial 产物（`.pt` 或 `jsonl`），聚合成 CSV，执行 objective 选 best。

### 7.3 MPD 是否需要轻量级更改？（三档选项）

- **0 改动（可用，但门槛高）**：继续输出 `.pt`，DMEval 用 torch 读取。  
  适合：你短期只做 MPD，且环境里已有 torch。

- **轻量改动（推荐）**：MPD 额外输出 `trial_metrics.jsonl`（或 `trial_metrics.csv`）。  
  DMEval 优先读轻量文件；`.pt` 仅在需要保存轨迹时才写。  
  适合：你希望 DMEval 更通用、更轻、更容易移植到其它项目。

- **中等改动（可选）**：MPD 也改为 Hydra config 体系（方案 B），并禁用 chdir。  
  适合：你最终明确“只服务 MPD”，追求最顺手的调参体验。

## 8. vNext 相对现有 DMEval 的“具体改进清单”（你到底要改什么）

下面按优先级给出“可落地”的改进点（先解决你当前最痛的地方）：

### P0（马上就该做：让你不再困惑）
1) **增加可解释命令**  
`dmeval explain --config ... [--override ...]`：打印 Hydra 合并后的最终配置（让你看到“Hydra 到底做了什么”）。  
`dmeval plan --config ...`：打印将要运行的 candidate 列表、每个 candidate 的关键 patch、预计输出目录。

2) **术语与日志标准化**  
在输出里固定使用 `candidate/run/trial/seed`，不要混用。  
在 `tune_manifest.yaml` / `compare_manifest.yaml` 里记录：场景、seeds、N、搜索空间、objective 版本等。

3) **搜索空间写法升级（保持兼容 grid）**  
在配置上引入显式字段：`tune.search.type = grid|random|optuna`。  
grid 仍然用你现在的 `grid:`，但为未来扩展留出结构。

### P1（论文工作需要：更公平、更可靠）
4) **阈值+优化（objective 结构化）**  
把 feasibility threshold 做成配置项（而不是写死在 simple.py），并支持多指标阈值。

5) **输出契约轻量化（减少 .pt 依赖）**  
推动 MPD 增加 `trial_metrics.jsonl` 输出；DMEval adapter 改为优先读取。  
这会显著降低你后续对接其它 planner 的成本。

### P2（提升效率/自动化：后期增强）
6) **引入 Optuna（贝叶斯调参）**  
实现 `SearchStrategy=optuna`（仍然串行）。  
把“budget/early-stop”做成配置。

7) **MPD 的 two-stage coarse→refine 策略插件**  
把你 sweep.py 的经验抽象成 `TwoStageStrategy` 插件（不依赖 sweep.py 本身作为数据来源）。

8) **（可选）MCP 控制层**  
把 `tune/compare/collect/plot` 暴露成工具接口，做成“实验助手”。  
注意权限与白名单，避免变成“任意命令执行器”。

## 9. 最小可用示例（vNext 文档应当保证你照做就能跑）

为了让你“不是只听概念”，vNext 的文档应该永远包含三条最小命令：

1) Stage I（单场景调参）  
2) Stage II（跨场景对比）  
3) collect/plot（对已有结果聚合与画图）

并且每条命令后面都写清楚“你应该去哪个目录检查产物是否生成”。

## 10. 最后：这份新架构为什么比你原 sweep.py 更适合写论文/给导师看

你的论文/答辩最怕的不是“跑不出结果”，而是别人质疑：
- 你是否公平比较（是否调参、是否同 seeds、是否统一口径）？
- 你是否可复现（配置是否完整、结果是否可追溯）？
- 你是否通用（是否只是一堆为 MPD 临时写的脚本）？

vNext 的核心价值是：把这些“学术可信度”变成工具的默认行为（结构化配置、两阶段流程、标准化产物、可解释与可追溯）。
