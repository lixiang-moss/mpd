DMEval 框架需求与架构设计
1. 总体目标与适用范围

DMEval 旨在提供一个通用且可扩展的评估工具框架，用于对各种运动规划算法进行评价。设计目标强调 通用性，当前示例应用是基于扩散模型的 MPD 系统，但整体架构与实现细节解耦，能够支持不同类型的推理器和任务场景。系统通过模块化设计，将配置、推理、结果解析、指标计算、统计分析等功能分离，每个模块通过清晰的接口相互协作。输出格式采用标准化文件（如 CSV、图表）以保证对比和分析的可重复性。

2. 模块划分
2.1 配置与调度模块

配置模块负责读取和管理实验配置参数，调度模块根据配置调度推理任务。建议使用 Hydra 等框架进行层次化配置管理：Hydra 是一个开源的 Python 框架，可通过配置文件和命令行动态创建分层配置。借助 Hydra 可以实现配置继承与覆盖，并通过多运行（multirun）功能一次启动多个实验。调度模块从配置中获取任务列表（例如不同算法、场景和超参数组合），并按照策略依次或并行启动推理任务。可采用 Hydra 的多运行功能或自定义调度器（如进程池/任务队列）来并发执行任务。接口说明：配置文件（YAML）中定义实验参数（算法名称、模型路径、场景参数等）；调度模块提供如 schedule_jobs(config_path, max_parallel) 的接口，根据配置生成并启动 InferenceRunner 任务。参数字段示例：

algorithm: 推理器标识（如“MPD”）；

model: 模型文件路径；

env: 场景或仿真环境参数；

runs: 每个配置的实验重复次数；

tuning: 超参搜索配置（见 2.7）。

2.2 推理运行模块（Inference Runner）

推理模块负责调用运动规划算法进行路径生成。它以 异步子进程 的方式启动推理程序，并监控其执行状态。可使用 Python 的 asyncio.create_subprocess_exec/ shell 等异步接口创建进程，利用 asyncio 并行运行多个命令。每个推理任务读取指定的配置（如算法参数和场景），执行后将结果（如轨迹数据、成功标志、耗时等）写入标准输出或指定文件（例如 .pt、.json 等）。接口说明：推理器应实现统一的输入/输出契约，例如接收 YAML/JSON 配置并输出结果文件。框架提供一个 InferenceRunner 类，它根据配置调用对应算法的可执行文件或 Python 函数，并捕获标准输出。参数字段示例：

cmd: 推理器执行命令或脚本；

timeout: 单次运行超时设置；

output_dir: 推理结果存放目录；

env_vars: 运行时环境变量配置。

2.3 结果解析模块

推理完成后，解析模块负责读取并提取推理输出数据。常见输出包括模型的 .pt 文件、日志或其他结果文件。解析器根据推理器规范加载数据（例如使用 torch.load 读取 .pt 文件、或解析 JSON/YAML 格式日志），并提取原始结果（轨迹点坐标、路径长度、平滑度、是否成功等）。解析器将这些原始结果封装成标准化格式（如 Python dict 或 pandas DataFrame），供后续指标计算使用。接口说明：提供 parse_results(task_id) 方法，输入推理任务标识，返回解析后的结果对象。解析器还应记录配置参数和任务元数据以便关联。

2.4 指标抽取与聚合模块

此模块基于解析后的结果计算评估指标。首先定义多个指标提取函数（如成功率、路径长度、平滑度、计算时间等），可以通过注册机制动态扩展。对于每个推理结果，指标提取函数输出一个指标名称和值。处理缺失数据时（例如失败运行缺少轨迹），需用默认值或 NaN 填充，以保证矩阵完整。指标计算结果按任务和算法汇总为表格形式（例如 DataFrame），并计算统计量（均值、方差等）。接口说明：提供 register_metric(name, function) 注册函数，function(result) -> value。此外提供 compute_metrics(results_list) 接口，输入解析结果列表，输出完整的指标矩阵。参数字段示例：

metrics: 指定需要计算的指标列表；

fill_missing: 缺失值处理方式（如用平均值或标记）。

2.5 多指标统计分析模块

统计分析模块对多个算法或配置的指标结果进行排序、分组和比较分析。主要功能包括：按照关键指标（如成功率、路径质量）对算法进行排名；对不同场景或参数集分组比较（如比较不同算法在相同场景的表现差异）；生成多指标综合评价（例如将成功率和路径长度纳入复合评分）。可根据需求输出排名 CSV（包括算法、各项指标及综合得分）和分组统计表。接口说明：提供 rank_algorithms(metrics_df, sort_by) 接口，根据指定指标排序输出排名列表。提供 group_compare(metrics_df, group_by) 接口，对指定分组维度（如场景）进行统计比较。

2.6 可视化模块

该模块自动生成对比图表，用于可视化比较不同算法/配置的评估结果。图表类型建议：

箱线图：展示连续指标（如轨迹长度、平滑度）的分布情况，可以并列比较多算法的分布。

条形图：用于对比算法的离散指标（如成功率、有效率），或聚合指标（如平均路径长度）。

折线图：展示指标随某一参数（如搜索步数、迭代次数）变化的趋势，例如在超参调优时跟踪性能随步数增长。

热力图：对超参数网格搜索结果进行可视化，将两个参数值对应的性能显示为颜色。例如显示不同学习率和迭代步数下的成功率。

可视化模块读取统计分析结果，使用 Matplotlib、Seaborn 等库自动绘制图表，并保存为图片文件（PNG、PDF 等）。接口说明：提供 plot_metric(metric_name, data, chart_type) 接口，根据指定指标和图表类型生成图形。支持通过配置文件（JSON/YAML）指定需要绘制的指标集合及样式（颜色、标注）。图表输出目录与其他结果文件统一管理。

2.7 可选模块：自动超参优化模块

自动调参模块为评估工具提供超参数搜索功能，可选实现。该模块预设搜索接口，支持网格搜索（Grid Search）和贝叶斯优化等策略。可借助 Optuna 等框架来执行优化。设计上提供统一的调参接口：给定待调参数空间和目标函数（如成功率最大化），自动调用推理模块多次实验并记录指标。接口说明：HyperParamOptimizer 类支持方法如 optimize(objective_func, param_space, strategy)，其中 strategy 可选 "grid" 或 "bayesian"。该模块与主调度模块结合，将每一组超参数作为一次推理任务提交。参数字段示例：

param_space: 待调参数及其取值范围；

objective: 优化目标指标名称；

n_trials: 最大实验次数；

tuner: 调参策略类型（grid/bayesian）。

3. 输入输出格式

输入格式：系统主要输入为 Hydra YAML 配置文件 和推理器输出文件。配置文件定义实验参数、算法设置、调参空间等（见 2.1 节）。推理器输出常见为二进制文件（如 .pt）或日志、JSON 输出等（具体格式由推理器决定）。

输出格式：主要输出包括：

指标 CSV 文件：每行对应一次推理运行，列为各项指标（如成功率、路径长度等）及配置参数。可用表格展示所有运行数据。

排名 CSV 文件：按照成功率、路径质量等关键指标对算法或配置进行排名，输出排名结果的 CSV 文件。

图表文件：根据可视化模块生成的比较图（PNG/PDF）。

分析摘要（可选）：可生成简要的文本或 HTML 报告，汇总关键指标和结论（非强制）。

示例：metrics.csv 包含列 [算法, 场景, 超参1, 成功率, 平均长度, 平均平滑度, 平均时间]；ranking.csv 按成功率降序列出 [算法, 成功率, 排名] 等。

4. 可视化输出建议

在指标维度和可视化模块设计中，可参考以下建议：

对于连续型指标（轨迹长度、平滑度），使用箱线图比较不同算法的分布；

对于二值或频率型指标（成功率、命中率等），使用条形图或堆叠柱状图展示；

对于变化趋势分析（如随迭代步数变化的耗时），使用折线图；

对于超参数组合效果展示，使用热力图将两个参数与性能关联展示（如成功率的色块图）。

5. 可扩展性说明

为实现通用和可扩展的设计，框架在多个模块中采取了解耦策略：

推理器接口：定义标准的输入/输出契约。所有推理器（MPD、其他轨迹生成算法）只需通过一个包装器将自身与框架对接。例如，统一规定推理器从 YAML 配置读取参数并将结果写入指定格式文件；框架为新推理器提供接口实现模板，只需封装具体执行过程。

指标接口：采用插件式注册机制，允许用户自定义指标提取函数。新增指标时，只需实现对应函数并注册到框架，即可自动在指标抽取模块使用，保持核心逻辑不变。

调参模块：默认提供网格搜索和贝叶斯优化两种策略，并通过统一接口（如基类 Tuner）支持后续扩展。用户可实现新的优化算法（如遗传算法）并注册进调参模块。

可视化配置：图表生成逻辑由外部配置文件（JSON/YAML）控制，例如指定要绘制的指标、图表类型和样式。这样可以在不修改代码的情况下，通过调整配置扩展和定制可视化输出。

6. 可拓展/待补充

评估指标的具体选择及权重设定：指标类型、权重等可通过配置指定，本设计仅给出接口，具体配置方案待定。

自动调参的搜索空间与目标函数：搜索空间范围和优化目标根据不同任务需求配置，需后续补充确定。

图表样式与报告输出格式：具体的配色、字体、报告模板等可在后期根据用户需求指定。

7. 设计决策依据说明

以下设计决策主要基于已有需求文档和常见的系统设计模式推断：

采用 Hydra 作为配置与调度基础（需求中提及支持 Hydra），因为 Hydra 能够通过配置文件和命令行动态组合配置。它的多运行功能便于一次性生成多个任务。

推理运行使用 异步子进程（例如 Python 的 asyncio）来并行处理多条任务（需求提到异步执行），这符合对并发处理的要求。

输出格式采用通用的 CSV 和图像文件，既方便分析工具处理，也便于结果共享，无需依赖特殊软件。

模块化和接口化的设计来自对可扩展性要求的推断：现有需求列明了多种功能模块（见第2节），说明系统应支持插拔式扩展。

可视化图表类型的建议（箱线图、条形图等）来自常见统计分析实践，满足对指标比较的直观需求。

HyperParam 模块的设计依据需求中对自动化调参的提及，结合 Optuna 这类框架的典型能力制定。

上述设计意图参考了需求文档中的功能点，并结合 Python 生态中常用方案（Hydra 配置管理、asyncio 并行执行、Optuna 调参框架等）进行集成，以实现一个通用、高效且可维护的评估工具架构。
